# Frontend conventions

Convenciones del frontend de libros-iselk: Next.js 14 (pages router) + React 18 + **Mantine 7** (ADR-0011) + Tailwind 3 acotado a layout.

**Estado**: seed. Este doc arranca con las reglas del stack (T3 + Mantine) y **crece con cada pantalla aprobada** — los sub-patrones atados a una feature concreta se consolidan acá cuando esa feature se construye y el usuario la valida. No anticipar patrones de features que todavía no existen.

## Mantine — la regla central

Paquetes instalados: `@mantine/core`, `@mantine/hooks`, `@mantine/form`, `@mantine/modals`, `@mantine/notifications` (major 7, pineada — misma que datawalt-app, la referencia del Operador). Otros paquetes Mantine (`dates`, `charts`, `carousel`) se agregan **cuando una feature los necesite**.

- **Componentes de UI** → siempre de `@mantine/core`. NO escribir a mano un componente que Mantine ya provee; NO reintroducir shadcn/Radix/CVA (retirados en ADR-0011).
- **Providers y estilos, una sola vez en `_app.tsx`**, en este orden de imports (el orden importa — los estilos Mantine se importan DESPUÉS de `globals.css` para ganar al preflight de Tailwind, patrón probado en datawalt-app):
  ```tsx
  import "~/styles/globals.css";        // Tailwind
  import "@mantine/core/styles.css";
  import "@mantine/notifications/styles.css";
  ```
  Árbol: `MantineProvider theme={theme} defaultColorScheme="light"` → `ModalsProvider` → `<Notifications />` + la app. `ColorSchemeScript` va en `src/pages/_document.tsx`.
- **PostCSS queda solo-tailwind** (sin `postcss-preset-mantine`): no escribimos CSS propio con mixins de Mantine. Si algún día hace falta, se agrega en ese momento.
- Estilos por componente: props del sistema de Mantine (`p`, `mt`, `gap`, `c`, `fw`, `size`, `visibleFrom`/`hiddenFrom`…) o clases Tailwind de layout. **No** crear CSS Modules salvo decisión registrada acá. **Decisión registrada (identidad «El Talonario»)**: los componentes de la gramática de marca en `src/components/landing/` (plumón, perforación, sello, talonario vivo, teléfono-tienda, chip de ticket, boleto CTA, bandas) SÍ pueden usar un **CSS module acotado**, pero **solo con CSS vars del theme** (`--mantine-color-*`, `--font-*`) — cero hex propio. Es la única familia de componentes con CSS module; el resto sigue con props Mantine.

## Theming

- El theme base vive en **`src/styles/theme.ts`** (`createTheme`): paleta **«El Talonario»** (`primaryColor: "sorteatelo"` = cobalto `#2b3fbf` en el índice 6, `primaryShade: 6`, `autoContrast: true`), acento `amarillo` (`#ffc530`), neutrales fríos (`gray` frío con tinta-suave `#565b68`, escala `hundido` celeste `#eef2fb` para el fondo del chrome, `black: #191b22` = tinta), tuplas semánticas (`exito` teal `#1d7a70` / `pendiente` ámbar `#a06b08` / `premio` = amarillo de marca, override de `red` a ladrillo `#c03e2e`), fuentes por **CSS var** (`var(--font-instrument)` texto, `var(--font-display)` headings = Bricolage 800, `var(--font-mono)` = IBM Plex Mono; el theme NO importa `next/font` — el loader vive en `fonts.ts`/`_document.tsx`), `defaultRadius: "md"`, `respectReducedMotion: true`. **`primaryShade: 6` está alineado con `tenantTheme.generarEscalaColor`** (base del tenant en el índice 6) — el `filled` per-tenant sale EXACTO en su `colorPrimario`. **`docs/design.md` §2/§3 es la fuente de verdad visual.**
- Color SIEMPRE vía tokens del theme (props `color`/`c`/`bg`, CSS vars `--mantine-color-*`), **nunca hex inline** ni clases de color Tailwind. `color="red"` reservado para errores/destructivo; "pendiente" nunca en rojo (usa `pendiente`).
- **Semántica de comercio**: los estados de orden/tienda se pintan con los mapas `ESTADO_ORDEN_COLOR` / `ESTADO_TIENDA_COLOR` exportados desde `theme.ts` (los consumen `estado-badge.tsx` / `estado-tienda-badge.tsx`) — no hardcodear el color de un estado en el componente.
- **Theming per-tenant (seam D13)**: el storefront arma su theme por request con `mergeThemeOverrides(themeBase, overrideDesdeTenant)` — los colores/logo del tenant son **dato del modelo `Tenant`**, jamás código. El panel/apex usan el theme de la Plataforma, SIN override.
- **Color-desde-dato en el panel**: los colores de MARCA del tenant (`colorPrimario`/`colorAcento`) son datos que el Organizador elige, no tokens — por eso pueden aparecer como hex en la UI del panel (el swatch del chip de tienda, `ColorSwatch color={colorPrimario}`) y editarse con `ColorInput`. Esto NO afloja «nunca hex inline»: la regla protege los tokens de NUESTRA UI, no el valor arbitrario de una marca ajena.
- **La marca se edita en dos superficies, con UNA fuente de atajos**: la card «Tu tienda» (`admin/configuracion.tsx`) y el panel Tema del editor (`panel-tema.tsx`) escriben las MISMAS columnas `Tenant.colorPrimario`/`colorAcento`. La paleta sugerida vive en **`~/lib/coloresMarca` (`SWATCHES_MARCA`)** y la importan las dos: si cada pantalla llevara su propio array, el mismo campo ofrecería atajos distintos según por dónde se entre (el drift admin↔builder que admin-bases-pdf F06/D7 vino a matar). Como son columnas y no Documento de Página, **guardar es aplicar**: no hay borrador que publicar para un color.
- **Fondo por color scheme**: para un fondo que difiera entre claro/oscuro (ej. el celeste hundido del chrome del panel/login), usar la función CSS `light-dark(claro, oscuro)` de Mantine 7 con tokens en `styles`/`style` — `light-dark(var(--mantine-color-hundido-1), var(--mantine-color-dark-8))` — no selectores propios por scheme.
- **Tailwind acotado a layout**: `flex`, `grid`, `gap-*`, `p-*`/`m-*`, `max-w-*`, responsive (`lg:`), `truncate`, `break-words` (su contraria: dejar envolver un dato largo que no se debe cortar), `tabular-nums`, **alineación de texto** (`text-right`/`text-center` — `text-align` es layout; en celdas de tabla conviven con el `ta` de Mantine, cualquiera de los dos vale) y `whitespace-pre-wrap` para texto preformateado versionado (ToS, bases). Los **`screens` de Tailwind están sincronizados con los breakpoints em de Mantine** (`xs 36em / sm 48em / md 62em / lg 75em / xl 88em`, patrón datawalt-app) — así los `lg:` de layout coinciden con `visibleFrom`/`hiddenFrom` y `AppShell`. **Prohibidas** sus clases de color/tipografía/sombra y las clases interpoladas (`bg-${x}` no sobrevive el purge). Composición condicional con `cn()` de `~/lib/utils`.
- **Motion (dependencia `motion`, ex framer-motion)**: SOLO para las entradas de sección de la **landing pública** (fade + translate leve, una definición reutilizada). **Acotado a la landing** — no importar `motion` en el panel ni en el storefront. Siempre respetar `prefers-reduced-motion`: con reduced-motion las secciones aparecen completas, sin animar (nunca ocultas).

## Iconografía

- **`@tabler/icons-react` es la única librería de íconos** (lucide se retiró con shadcn). Siempre **named imports**, tree-shakeado:
  ```tsx
  import { IconShoppingCart } from "@tabler/icons-react";
  ```
  **Nunca** importar el barrel completo. En botones/inputs de Mantine van en `leftSection`/`rightSection`.

## Estructura de componentes y páginas

- Páginas en `src/pages/` (pages router). Componentes reutilizables en `src/components/`.
- **Componentes de feature en `src/components/<feature>/`** (ej. `src/components/admin/`); `src/components/` raíz para lo transversal.
- **Orden interno de una página**: imports → hooks → estados (`useState`/`useForm`) → queries (`api.x.useQuery`) → mutations (`api.x.useMutation`) → effects → funciones → constantes → return.
- Constantes estáticas fuera del componente. Imports siempre con alias `~/*`.
- El shell del panel es `AdminLayout` (`AppShell` de Mantine: navbar colapsable en mobile con `Burger` + `useDisclosure`).

## Data fetching (tRPC)

- Hooks de `~/utils/api` (`api.<router>.<procedure>.useQuery` / `useMutation`).
- En `onSuccess` de mutations: **invalidar/refetchear** las queries afectadas vía `utils` (`api.useUtils()`). Invalidar TODAS las queries que la mutation pueda afectar, incluso indirectamente.
- **Toda pantalla con datos resuelve los tres estados**, no solo el happy path:
  - **loading** → `Skeleton` de Mantine que replica la estructura real (evita layout shift);
  - **error** → mensaje en `c="red"` + botón "Reintentar" (`refetch`);
  - **data vacía** → estado vacío con ícono (Tabler) y mensaje en voz al usuario, no un hueco en blanco.
  - **no autorizado** (pantallas gateadas por rol/membresía, p. ej. Operador o el panel de tienda) → si el procedure responde `FORBIDDEN`/`UNAUTHORIZED`, mostrar un estado explícito "no tienes acceso" (no dejarlo caer al skeleton perpetuo ni a un error crudo) — es la 4ª rama de estas pantallas.
- **Diálogos con submit**: el botón con `loading={isPending}` (OR compuesto si hay varias mutations) — Mantine deshabilita y muestra spinner en un solo prop.
- **Listas paginadas por cursor** (ver `backend-conventions.md` § Paginación por cursor): `useInfiniteQuery` — `getNextPageParam: (ultima) => ultima.nextCursor ?? undefined`; filas con `data?.pages.flatMap((p) => p.items) ?? []`; UI **forward-only con botón "Cargar más"** (`hasNextPage` + `fetchNextPage()`, `loading={isFetchingNextPage}`), no un paginador de saltar-a-página-N. Ej.: `src/pages/admin/ventas.tsx`.
- **Mutation por-fila en una tabla** (una sola instancia de `useMutation` compartida por N filas): aislar el `loading` a la fila que la disparó con `mutation.isPending && mutation.variables?.<id> === fila.id` — nunca un hook por fila ni un `useState` de id-en-vuelo. El `loading` de Mantine ya deshabilita el botón (evita doble submit). Ej.: botón "Reenviar" de `src/pages/admin/ventas.tsx`.
- **Formularios hidratados desde una query** (editar config existente): la `useQuery` se declara antes del form y los datos se vuelcan con `form.setValues` / `initialize` en un `useEffect` cuando llegan. **Early-return en `isError` / sin-data ANTES de renderizar el form editable**: pintar el form en blanco con Guardar activo pisaría los datos reales con vacíos (regresión de pérdida de datos). Ej.: `src/pages/admin/configuracion.tsx`.

## Formularios

- Forms con más de un campo o con validación → **`@mantine/form`** (`useForm` con `initialValues` + `validate`), inputs cableados con `{...form.getInputProps("campo")}` y `<form onSubmit={form.onSubmit(handler)}>`. Un input suelto (ej. un buscador) puede seguir en `useState`.
- Errores de validación en el propio input (Mantine los pinta desde `getInputProps`); errores del server → notificación (ver abajo) o `Alert`.
- **Marcado de obligatoriedad — INVERTIDO en los forms públicos del storefront.** En el panel la marca es `withAsterisk` sobre lo obligatorio (ej. `src/pages/admin/sorteo.tsx`). En los forms que ve el **Comprador** la convención es la contraria: **lo OPCIONAL lleva `(opcional)` en la etiqueta y NADA lleva asterisco**. Razón: el correo del checkout es obligatorio y hoy no tiene asterisco (ADR-0004); ponérselo cambiaría el form de las Tiendas que no configuraron ningún campo, y marcar con asterisco solo los campos nuevos dejaría al correo como el único sin marca — se leería como «el correo es opcional», exactamente lo contrario. Así al Comprador le queda una sola regla: se responde todo salvo lo que dice `(opcional)`. Un `Checkbox` no lleva marca en ninguna de las dos direcciones (siempre está respondido). Ej.: `src/components/storefront/campos-checkout.tsx`.
- **Payload de un form de campos DINÁMICOS: se manda todo lo renderizado, sin filtrar los vacíos.** Cuando las claves del form las define un dato (los Campos de checkout del Organizador) y no el archivo, el cliente envía **una entrada por cada campo que renderizó**, incluidos `""` y `false` — qué cuenta como respuesta lo decide el server contra la definición vigente. Filtrar en el cliente sería opinar sobre algo que no le toca, y el primero en desaparecer sería un `Checkbox` desmarcado, que ES una respuesta. Además la propiedad es load-bearing: mandar todas las claves es lo que le permite al server distinguir «lo dejaste vacío» de «este campo ni existía en tu pantalla» (mensajes distintos). Ej.: `respuestasParaEnviar` en `src/components/storefront/respuestas-checkout.ts`.
  - **Contraste con el editor del page builder**, donde sí se usa `valor || undefined` al escribir props (`src/components/editor/form-props.tsx`): ahí el cliente es el DUEÑO del documento y la ausencia ES el valor canónico (borrar una prop la devuelve a su default del widget). En un form dinámico el cliente no es dueño de nada: solo transporta lo que el Comprador tipeó.
- **Qué se puede espejar en el cliente y qué no.** El espejo de cliente puede validar (a) **obligatoriedad** y (b) lo que el input **previene a nivel de TECLA** (`allowDecimal={false}` en un `NumberInput` entero, `type="tel"` + `inputMode`) — eso no duplica una verdad, impide tipear algo imposible. NO se espeja un **rango ni un formato** que obligue a repetir en el cliente un número que vive en el server (el tope de largo, el máximo, la pertenencia a una lista): sería mantener dos verdades y la que manda es la del server. Y **nunca** se corrige el valor tipeado **en silencio**: `min={0}` a secas en un `NumberInput` de Mantine reescribe el `-5` del usuario a `0` al salir del campo (el default es `clampBehavior: "blur"`), o sea le cambia el dato sin decirle nada. Ej.: `src/components/storefront/campos-checkout.tsx`.
  - **Cuando el input OFRECE un valor imposible, se quita la oferta — no se agrega una regla.** Los spinners del `NumberInput` dejan caminar de 0 hacia abajo con el mouse en un campo donde el negativo nunca es un dato; el fix es **`hideControls`**, que retira la escalera sin afirmar ningún rango. Es preferible a `min={0} clampBehavior="strict"`, la otra salida limpia, porque `strict` obliga a declarar un `min` — y ese número es justo el rango del server que este bullet prohíbe espejar. Tipear el guión a mano sigue siendo posible y lo rechaza el server, que es quien manda: el cliente le sacó la trampa al mouse, no se quedó con una segunda verdad. Resuelto así en el `NUMERO` del checkout (2026-07-25).
- **Forms con claves DINÁMICAS** (un sub-objeto cuyas llaves las define un dato, no el archivo): `validate` de `useForm` se escribe como **FUNCIÓN** que recibe los valores y devuelve el objeto de errores, no como el mapa `{campo: fn}` de siempre — no se puede enumerar en el archivo lo que el Organizador define en runtime. Los inputs se cablean con el path anidado (`form.getInputProps("respuestas." + clave)`) y los errores se devuelven con **esa misma ruta** (`respuestas.<clave>`). Acoplamiento invisible que hay que respetar: la clave **no puede contener un punto** — el punto es el separador de paths de `@mantine/form` y partiría la ruta en dos niveles inexistentes. Hoy lo garantiza el server, que deriva la clave con `slugificar` (`src/server/domain/camposCheckout/_clave.ts`, `[a-z0-9_]`) y la vuelve inmutable; si alguna vez la clave la escribiera un humano, esa restricción hay que validarla explícitamente. Ej.: `src/pages/checkout/index.tsx` + `erroresDeCampos` en `respuestas-checkout.ts`.

## Notificaciones

- Feedback de mutations con **`@mantine/notifications`**: `notifications.show({ message, color: "green" })` en éxito cuando el resultado no es evidente en la UI; `color: "red"` + mensaje accionable en error. No usar `alert()` ni estados de texto ad-hoc para errores de mutation.

## Diálogos y destructivos

- Modales con contenido/form → `Modal` de `@mantine/core`.
- **Confirmaciones destructivas** → `openConfirmModal` de `@mantine/modals` con `confirmProps: { color: "red" }`, título claro y `children` que diga QUÉ se va a borrar. No armar diálogos de confirmación ad-hoc.

## Idioma

- UI en **español** con tuteo (strings hardcodeados — no hay i18n).
- **Español con tuteo**: "tienes", "puedes", "elige" (no voseo).
- **Tono cercano chileno** (dirección «El Talonario», `docs/design.md` §8): microcopy y empty states pueden usar un registro humano y de contención, no solo texto funcional (ej. "Todavía no vendes nada — y está bien"). Evitar jerga SaaS y lenguaje de urgencia/escasez de rifa en el chrome de plataforma.
- **Excepción al hardcodeo**: el nombre de la app se consume SIEMPRE desde `APP_CONFIG` (`~/config/app` — `name`/`tagline`/`dominio`) — nunca literal en JSX/títulos. La marca ya está resuelta (Sortéatelo, «El Talonario» — cobalto/amarillo/tinta; ver `docs/design.md`).

## Formato de dinero

- **Los helpers viven en `~/lib/formato`** (única fuente): `clp(monto)` formatea CLP con `Intl.NumberFormat("es-CL")` y acepta el **string `Decimal`** del server o un `number` ya cruzado; `num(n)` formatea enteros con separador de miles (conteos, NO montos); `fechaHora(d)` da fecha+hora corta es-CL; `fecha(d)` da fecha corta SIN hora es-CL (rangos de fechas, ej. el sorteo). **Nunca** re-crear un `Intl.NumberFormat`/`Intl.DateTimeFormat` inline en una página ni concatenar `$` a un monto ya formateado.
- Montos con **`tabular-nums`** (clase Tailwind) en tablas y listas — las columnas de precios no "bailan".
- **Input de monto** (crear/editar precio): `TextInput` de Mantine con `leftSection={"$"}` (afijo visual, no parte del valor), `inputMode="numeric"` (teclado numérico en móvil) y clase `tabular-nums`. El valor se maneja como **string** en el form y viaja como string al server (CLP entero ⇒ `Decimal`), jamás como `number`. **NO usar `NumberInput`** para dinero — su value `number` invita a aritmética prohibida en el cliente. Ej.: `src/pages/admin/productos.tsx`.
- El dinero del dominio es `Decimal` (precio, total, IVA, comisión de Flow, neto). El cruce a `number` ocurre SOLO en el borde de presentación para formatear, y es seguro porque CLP no tiene decimales — jamás hacer aritmética con ese `number` ni mandarlo de vuelta al server (ver `CLAUDE.md` § Regla de oro y `CONTEXT.md` § Dinero).

## Carrito y stepper de cantidad (storefront)

- El carrito del Comprador es estado de CLIENTE per-slug (localStorage `carrito:<slug>`, sin modelo `Cart`, ADR-0004). Cada `ItemCarrito` lleva `cantidad` (≥1); el contexto expone `agregar` (inicia en 1), `setCantidad` (clampeada a `[1, MAX_CANTIDAD_POR_ITEM]`) y `quitar`.
- Ajustar cantidad → **`StepperCantidad`** (`src/components/storefront/stepper-cantidad.tsx`): par de `ActionIcon variant="default"` (−/+) con un `Text` `tabular-nums` en medio; deshabilita `−` en 1 y `+` en el tope; lee/escribe vía `useCarrito`, con `aria-label` en ambos botones. Reusado en carrito-drawer, catálogo, detalle y checkout.
- **I4**: el stepper solo cuenta UNIDADES, nunca opera dinero. `MAX_CANTIDAD_POR_ITEM` se duplica a propósito entre cliente (`carrito.tsx`) y server (`checkout/schemas.ts`) — el cliente no puede importar código server; ambos lo documentan como espejo del `max` de Zod.

## Subida de assets al bucket público (panel)

- El panel sube assets públicos por **presigned PUT + confirmación** (mismo patrón que el PDF de producto): se pide la URL prefirmada, se hace el PUT directo (los bytes no pasan por el server) y se confirma server-side. Dos hooks, uno por familia de asset: `useSubirImagenMarca` (`~/components/admin/use-subir-imagen`) para logo/hero/portada/premio, y `useSubirBasesSorteo` (`~/components/admin/use-subir-bases`) para el **PDF de bases** del sorteo (ADR-0008). La allowlist de Content-Type es ESPEJO del server (`CONTENT_TYPES_IMAGEN` / `CONTENT_TYPE_BASES`): el cliente no importa código server y el server re-valida en el input Zod Y en el service. El `<FileInput>` usa `accept={ACCEPT_IMAGEN}` / `accept={ACCEPT_BASES}`.
- **Un hook por familia, no un hook genérico**: mezclar imágenes y PDF en una sola allowlist abriría `application/pdf` a los destinos de imagen, que es justo lo que el invariante del bucket público prohíbe. La separación en el cliente espeja la del server.
- Dos modos: **inmediato** (`AssetUploader` — el recurso ya existe: logo/hero/premio; sube al elegir archivo e invalida su query) y **diferido** (portada de producto — se sube DESPUÉS de crear/actualizar, porque la key es per-recurso y necesita el `productId`).
- El **mismo recurso puede necesitar los dos modos**: las bases del sorteo van diferidas en el form de creación (la key es per-raffle y no hay id todavía) e inmediatas en el panel del sorteo activo (`BasesUploader`). En el modo diferido, el `catch` del submit debe **invalidar igual**: el recurso pudo crearse y fallar solo la subida, y la UI no puede quedar mintiendo.
- **Vista previa según el tipo**: una imagen se miniaturiza (`VistaPreviaAsset`); un PDF no — su estado se comunica con un `Badge` de token semántico (`exito` cargado / `pendiente` faltante) + enlace para abrirlo. Ver `bases-uploader.tsx`.

## Chrome del panel «Oscuro + calmo» (admin)

- Superficie base del panel = **`PanelCard`** (`src/components/admin/panel-card.tsx`): `Card` sin borde, `radius="lg"`, sombra del token único `SOMBRA_PANEL`. NO usar `Card withBorder` en el panel; NO overridear el `Card` global del theme (rompe storefront/landing).
- **2ª excepción a "cero hex inline"**: `SOMBRA_PANEL` (rgba de la tinta con alpha) es el token único de elevación del panel — un solo lugar para ajustar la sombra (junto a los assets SVG de §9 de design.md, es la única familia con valores fuera del theme).
- **Rail colapsable**: `AppShell` con `navbar.width` dinámico (76 icon-only ↔ 256 icon+label), estado persistido con `useLocalStorage`; icon-only solo desktop (`useMediaQuery` del breakpoint lg). La animación de ancho es CSS puro en `styles.navbar` (no la librería `motion`), gateada por `useMediaQuery("(prefers-reduced-motion: reduce)")` (no `motion-safe:`, porque vive en props inline del AppShell).
- **Data-viz**: `@mantine/charts` — `Sparkline` en KPIs con serie; `BarChart` 14d. Para colorear UNA barra distinto (ej. "hoy" amarillo) se usa el truco de serie apilada de 2 (una serie por color, la otra en 0), porque `getBarColor` colorea por valor, no por posición.
- **Countdown del panel** (`admin/index.tsx`): calmo, sin segundos (§8, evita urgencia). Candidato a extraer a componente compartido cuando F05 lo necesite.
- **Tablas del panel — dos variantes de `PanelCard`**: (a) tabla CON header in-card (título + descripción, a veces un botón "Ver todas") → `PanelCard` con padding default (`lg`) y la tabla SIN `pl-6`/`pr-6` (la padding de la card provee el borde); ej. "Últimas ventas" del Resumen, participantes de Sorteo, Operador. (b) tabla full-page SIN header in-card (el título vive en `AdminLayout`) → `PanelCard padding={0}` con `pl-6`/`pr-6` en la primera/última celda (edge-to-edge, evita whitespace muerto sobre el thead); ej. Ventas, Productos.
- **Inset borderless dentro de una `PanelCard`**: para un bloque destacado ANIDADO (caja del ganador en Sorteo, estado de la credencial en Configuración) usar `Paper` SIN borde + `bg="var(--mantine-color-default-hover)"` + `radius="md"` (un paso menor que el `lg` de la card) y SIN sombra. `SOMBRA_PANEL` es solo para superficies top-level: una sombra anidada leería como "card dentro de card", que la gramática evita.
  - **Variante "un inset por FILA"**: el mismo inset se repite como fila de una lista (`Stack gap="xs"` de `Paper` insets), no solo como bloque único. El criterio de elección NO es la cantidad de filas sino **la forma de la fila**: datos TABULARES (mismas columnas alineadas, comparables entre sí) → `Table` (ver las dos variantes de arriba); **fila COMPUESTA** (contenido apilado a la izquierda —etiqueta + metadatos— y controles a la derecha —switch, flechas de orden, íconos de acción—) → un inset por fila, que da la superficie que la fila necesita sin inventar columnas falsas. Mismas reglas del inset: sin borde, sin sombra, `radius="md"`. Ej.: «Campos del checkout» en Configuración (`src/components/admin/campos-checkout.tsx`).
- **Detalle de UN registro de una tabla → `Drawer` por la derecha, NO fila expandible.** Para mostrar todo lo de una fila (las líneas de una compra, pares etiqueta/valor de largo variable) se abre un `Drawer` de `@mantine/core` con `position="right"`, `title` en un `<Text fw={600}>`, `padding="md"` y `size` por densidad (`md` para un detalle que entra en una pantalla). Lo que decide NO es el gusto sino el **contenedor**: la tabla vive dentro de un `Table.ScrollContainer minWidth={640}`, así que una fila expandida hereda ese ancho mínimo y en un teléfono obliga a **scroll horizontal para leer justo el dato que se vino a ver**. El Drawer se lleva el detalle fuera de la tabla y lo apila en vertical. Es además la **segunda superficie top-level que hospeda el inset borderless** (la regla de arriba dice «dentro de una `PanelCard`»): adentro del Drawer los bloques van con el mismo `Paper` sin borde + `bg="var(--mantine-color-default-hover)"` + `radius="md"` y sin `SOMBRA_PANEL`. Ej.: `src/components/admin/detalle-venta.tsx`, abierto desde `src/pages/admin/ventas.tsx` (el precedente de forma es el carrito del storefront, `carrito-ui.tsx`).
  - **Estado del detalle**: `useState<string | null>(id)` + `useDisclosure()`, y la fila se **deriva por `find`** sobre los datos vivos de la query — no se guarda el objeto. Así el Drawer sigue el refetch (una orden que pasa a PAGADO se actualiza a la vista) en vez de mostrar una copia congelada. El id **no se limpia al cerrar**: vaciarlo junto con `opened` dejaría el panel deslizándose hacia afuera en blanco. Mismo par ya usado en el modal de importar participantes (`admin/sorteo.tsx`).
  - **Un dato que en la CELDA se trunca, en el detalle se deja envolver**: en la tabla `truncate` es correcto (es una columna que hay que encajar); en el Drawer ese mismo dato es lo que el Organizador vino a leer y a copiar, así que va con `break-words`.
  - **Acciones de fila en una tabla del panel: `Button` de texto, no `ActionIcon`** — `variant="subtle" color="gray"` para la acción de LECTURA (abrir el detalle) y `variant="light"` para la que hace algo (reenviar, con su `leftSection`), ambas `size="xs"` dentro de un `Group gap="xs" justify="flex-end"`. Un ícono suelto en una fila obliga a adivinar, y el panel no usa `Tooltip` en icon-only. `ActionIcon` queda para las **filas-inset densas**, donde los mismos controles se repiten en cada fila y la etiqueta sería ruido (`campos-checkout.tsx`). El «**—**» se reserva para celdas de **DATO** vacío (una comisión que todavía no existe), nunca para una acción ausente: una acción disponible siempre se ofrece.
  - **Un dato ausente en el DETALLE omite la línea; el «—» es de la CELDA, no del Drawer.** El guion existe para que la **columna** no se desalinee cuando una fila no tiene el dato; dentro del Drawer no hay columna que alinear, así que la línea simplemente no se renderiza (`{venta.comision !== null && (…)}`) — una venta PENDIENTE muestra Total y nada más, igual que la sección de respuestas del checkout cuando la orden no tiene ninguna. Corolario que sí obliga: **un dato que la tabla esconde por breakpoint hay que REPONERLO en el detalle**. Las columnas «Comisión» y «Te queda» se ocultan bajo `md`, así que sin esas dos líneas en el Drawer el Organizador no tenía NINGUNA vía de ver cuánto le queda de una venta desde un teléfono. Ej.: `src/components/admin/detalle-venta.tsx`.
- **Peso del botón en el header de página (`AdminLayout actions`)** — el `variant` comunica jerarquía, no gusto: **CTA de la página** (la acción que la pantalla viene a proponer; «Agregar producto» en Productos) → `Button` filled, o sea sin prop `variant` (el default del theme); **utilidad sobre lo que YA está listado** (no crea nada, opera sobre el conjunto en pantalla; «Exportar CSV» en Ventas) → `variant="default"`. Dos filled en headers hermanos borran la diferencia entre «crear» y «bajar una copia». Lo que comparten ambos: `leftSection` con ícono Tabler `className="size-4"` y la etiqueta envuelta en `<span className="hidden sm:inline">` (icon-only bajo `sm`). Si la utilidad no tiene sentido con la lista vacía va `disabled` — un archivo con solo el encabezado se lee como que el export está roto. El slot también hospeda elementos que no son botones (`EstadoTiendaBadge` en Resumen).

## Degradación elegante de imágenes (storefront)

- Toda imagen del storefront es opcional; su ausencia cae a un **gradiente temático** (`gradienteTematico` de `~/styles/tenantTheme`, derivado de la escala del `colorPrimario` vía CSS vars `--mantine-color-marca-*` / `--mantine-primary-color-*`) — **nunca un `<img>` roto** (design.md §5.2). Cero hex inline.
- Texto/ícono de contraste SOBRE un gradiente: `c="white"` en componentes Mantine (token), pero `color="var(--mantine-color-white)"` en íconos Tabler (no pasan por el resolver de tokens de Mantine).

## Crear/editar y listar en el panel (sorteo)

- **Fieldset compartido crear/editar**: cuando un form de creación y uno de edición comparten campos, extraer un componente que reciba `form: UseFormReturnType<T>` (de `@mantine/form`) y renderice los inputs cableados con `form.getInputProps`. Cada form (crear/editar) mantiene su propio `useForm`; el fieldset es presentación pura. Ej.: `CamposSorteo` en `admin/sorteo.tsx`.
- **Modal de selección desde una lista pasada** (arrastre/import): `Modal` de `@mantine/core` con `Radio.Group` para elegir UN registro anterior, más un botón de escape ("Empezar de cero"). La selección vive en `useState`; se aplica al confirmar, no al elegir el radio. Ej.: importar participantes de un sorteo anterior en `admin/sorteo.tsx`.
- **Sección "Historial"**: bajo el panel de gestión del recurso ACTIVO, una `PanelCard` con tabla de los registros cerrados/pasados (aquí, sorteos ejecutados con su ganador). Se alimenta de una query "listar todos" scoped por tenant, separada de la query del recurso activo.
- **Fecha+hora sin `@mantine/dates`**: para capturar un `DateTime` sin sumar dependencia, usar `TextInput type="datetime-local"`; el valor viaja como string en el form y se convierte a `Date` al enviar (superjson lo serializa). Helper `aInputDateTime(d)` para hidratar el input al editar.

## Metadata SEO de la landing del apex

- La metadata de la landing vive en **`src/components/landing/seo.ts`**, sibling de `copy.ts`, no dentro del componente: son DATOS derivados y el `<Head>` solo los imprime. Es el primer (y por ahora único) módulo de SEO del repo — el storefront de tenants NO lo importa (alcance apex).
- **El JSON-LD se DERIVA del copy, nunca se escribe a mano.** El `FAQPage` es un `.map` sobre el array `FAQ` y el precio del `Offer` es el mismo número que la UI formatea con `clp()`. Un bloque escrito aparte se desincroniza en la primera edición y deja a Google mostrando en sus resultados una respuesta que la página ya no dice.
- Los `<script type="application/ld+json">` van en el **BODY**, no dentro de `next/head`: es la forma que documenta Next para el pages router y evita la deduplicación que `next/head` aplica a los tags especiales. `dangerouslySetInnerHTML` es seguro mientras el contenido sea copy NUESTRO (un test prohíbe `</script` en el JSON); **si algún día lleva datos de tenant hay que escapar `<` de verdad**, no solo el cierre.
- Toda URL de metadata (canonical, `og:image`) es **ABSOLUTA** y sale de `APP_CONFIG.dominio`. Los crawlers sociales no resuelven rutas relativas ni rasterizan SVG: `og:image` apunta a un PNG 1200×630 (`npm run og:png` lo regenera desde `public/og.svg`).

## Copy de superficie de marca: invariantes testeados

- El copy de la landing (`src/components/landing/copy.ts`) tiene **reglas de negocio y legales dentro del texto** (palabra prohibida, una sola mención del procesador, promesas económicas con su apellido). Se blindan con tests que leen los **exports aplanados** del módulo, no el archivo crudo — así sobreviven a una reescritura completa del copy. Ver `src/__tests__/components/landing-copy.test.ts`.
- **Antes de afirmar que el usuario VE algo, verificar la pantalla.** En esta task el copy vivo prometía que el Comprador "ve su número en pantalla y en su correo" y ninguna superficie lo muestra; el primer reemplazo introdujo la misma mentira sobre el panel. Una promesa de UI en el copy se paga en soporte: se verifica contra el componente/use case, no contra la intención.
- **Remate de sección con plumón**: cuando una banda de la landing cierra con una frase-promesa ("Todo esto, **en una tarde.**", "**Menos de mil pesos al día.**"), va en un `Text` más pesado que el cuerpo CON `Plumon` sobre la parte destacada. Sin el plumón, un remate con el mismo tratamiento tipográfico que los títulos de card se lee como un ítem huérfano de la grilla.
